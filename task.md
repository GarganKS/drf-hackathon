# Командний челендж: API-спринт за 5 годин

**Формат:** хакатон на один день, 6 уроків. **Чотири команди по 4 людини**, склад
визначає викладач. Домен жеребкується. Наприкінці дня команди атакують API одна одної,
лагодять пробите і показують результат.

**ШІ використовувати можна і треба.** Саме тому робота влаштована так, що згенерований
код сам собою нічого не виграє: бали дає те, що витримало чужу атаку, і те, що ви
здатні пояснити вголос. Код, який ви не розумієте, ви не захистите — і це не погроза,
а механіка дня.

---

## Правила

1. **Домен жеребкується** — обговорення «а що ми робимо» заборонене, це з'їдає годину.
2. **Готове = показане.** Те, чого не показали на демо, не існує. Слайдів немає,
   показується працюючий код.
3. **Ви відповідаєте за весь код команди**, незалежно від того, хто його написав —
   ви, товариш чи модель. На демо кожен отримує питання **з чужої частини** коду.
4. **Новий репозиторій зі стартового скелета** (`starter/`). У скелеті вже налаштовані DRF,
   вхід через JWT, SQLite під одночасні запити і скрипти атаки — на це день не витрачається.
5. **Коміт від кожного, у свої файли.** Кожна роль володіє своїми файлами (таблиця ролей
   нижче), тож конфліктів злиття майже немає. Команда, де всі коміти від однієї людини,
   втрачає бали за «Командність».
6. **Два теги.** `attack` — наприкінці 4-го уроку: на ньому вас атакують. `final` — наприкінці
   5-го уроку: на ньому вас оцінюють. Після `final` код не змінюється.

## Домени для жеребкування

| № | Домен | Обмежений ресурс |
|---|---|---|
| 1 | Прокат велосипедів | справні велосипеди на станції |
| 2 | Паркінг | місця на рівні |
| 3 | Шкільна бібліотека | примірники книги |
| 4 | Автомийка | вікна запису на день |
| 5 | Спортзал | місця на тренуванні |
| 6 | Оренда інструментів | одиниці інструмента |
| 7 | Прокат настільних ігор | коробки гри |
| 8 | Лабораторія | місця на лабораторну роботу |

Будова всюди однакова: **каталог → заявка → підтвердження, яке займає ресурс →
скасування, яке його повертає**. Домени різні, тому списати нема чого.

## Головне правило дня: автомат станів заявки

```
            confirm                cancel
  draft ───────────────► confirmed ─────────► cancelled
    │                                            ▲
    └────────────────── cancel ──────────────────┘
          (ресурс не займали — нічого не повертаємо)
```

- Поле `status` має рівно три значення: `draft`, `confirmed`, `cancelled`.
- **Будь-який перехід, якого немає на схемі, повертає `409`.** `cancelled` — кінцевий стан.
- **Інваріант: ресурс зайнятий тоді й лише тоді, коли заявка в стані `confirmed`.**
  Будь-яка операція, після якої це перестає бути правдою, — помилка, навіть якщо вона
  повернула `200`.

Інваріант — ключ до закритої частини атаки. Перевіряйте кожну операцію вашого API
(не лише `confirm` і `cancel`) питанням: «чи лишився він правдою?»

## Етап 1 · Поріг — до кінця 2-го уроку

**Перші 30 хвилин — моделі всією командою за одним екраном.** Поки моделей немає,
решті трьох ролей нема на що спертися. Далі розходитесь по ролях.

- [ ] Дві моделі у зв'язку: каталог (із числовим полем залишку) і заявка зі `status`
- [ ] `ModelViewSet` + `DefaultRouter`, адреси під `/api/v1/`
- [ ] Читання каталогу відкрите, усе із заявками — лише з токеном
- [ ] Заявку видно **лише її власнику** (`get_queryset` + клас прав)
- [ ] Власник ставиться сервером у `perform_create()`, `owner` і `status` у тілі ігноруються
- [ ] `@action` `confirm` і `cancel` за схемою станів
- [ ] `seed_attack` створює акаунти й каталог, `contract.json` заповнений (див. README скелета)

**Контрольна точка в кінці 2-го уроку:** команда запускає на своєму API

```bash
python tools/attack_open.py --only 1,2,3,7,8,18,19
```

і показує результат викладачеві. Зелені рядки й робочий `seed_attack` — це бали порога.
Хто не має працюючого `confirm`, до етапу 2 не переходить, а доробляє поріг.

## Етап 2 · Витримати — до кінця 4-го уроку

Тут починається справжнє завдання. Усе нижче ШІ напише лише тоді, коли ви **самі
знаєте, що просити** — бо happy path він генерує, а ці випадки не передбачає.

### 1. Ресурс не можна продати двічі

Два одночасні підтвердження не мають вивести залишок у мінус, а одна заявка не має
підтвердитися двічі. Перевірка в Python (`if bike.available > 0:`, далі `save()`) гонку
**не** закриває — між читанням і записом встигає інший запит.

Захист має жити **в базі**. Найпростіший робочий прийом — **умовний `UPDATE`**:

```python
# update() повертає кількість змінених рядків; 0 означає «умова не виконалась»,
# і база вирішує це атомарно, без вікна між читанням і записом
Bike.objects.filter(pk=bike_id, available__gte=qty).update(available=F("available") - qty)
```

Той самий прийом стереже і **стан** заявки: `filter(pk=..., status="draft").update(...)`.
Обидва `UPDATE` — в одній `transaction.atomic()`: якщо другий не спрацював, киньте
виняток **всередині** блоку, і перший відкотиться.

`CheckConstraint` на невід'ємний залишок — страхувальна сітка, а не головний захист.
Якщо вона спрацює, Django кине `IntegrityError`, і без `except` це буде `500` — а `500`
на атаці рахується як пробій.

Ви це вже бачили: `F()` і гонка лічильника — ПР №2.8.5, `CheckConstraint` — ПР №2.8.6.

**Перевіряйте себе** скриптом зі скелета — він запускає справді одночасні запити:

```bash
python tools/race.py --item <id> --orders 10           # різні заявки на один елемент
python tools/race.py --item <id> --orders 10 --same    # одна заявка, 10 confirm
```

### 2. Негативні випадки

Повний перелік — рядки 1–20 [відкритої карти](attack-card.md). Кожен має повертати
осмислений код, а не `500`. Ганяйте `python tools/attack_open.py` проти себе скільки
завгодно — це специфікація, а не іспит.

### 3. Підготовка до атаки — останні 10 хвилин 4-го уроку

1. `git tag attack && git push --tags`
2. Посилання на репозиторій — команді, яка вас атакує (коло 1 → 2 → 3 → 4 → 1).
3. Ви отримуєте посилання на ціль і готуєте її у себе:

```bash
git clone <url> target && cd target && git checkout attack
python -m venv venv && source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate && python manage.py seed_attack
python manage.py runserver 8001
```

Атака йде **на вашому ноутбуці, на копії чужого коду**: мережа класу ні до чого, а
читати код цілі дозволено і корисно.

## Етап 3 · Атака — 5-й урок

| Хвилини | Що |
|---|---|
| 0–5 | `attack_open.py` проти цілі; викладач роздає закриту частину карти |
| 5–25 | шість перевірок закритої частини, коди — у таблицю на дошці |
| 25–35 | дві вільні атаки власного винаходу, суддя — викладач |
| 35–55 | **латання власного API** за результатами атаки на вас |
| 55–60 | `git tag final && git push --tags`, далі тільки показ |

Під час атаки поруч з атакувальниками сидить одна людина від команди-цілі
(зазвичай роль «Стійкість»): результат кожного рядка записується, коли обидві сторони
погодилися. Суперечку вирішує викладач повторним запуском.

## Якщо лишається час

- **клієнт**: сторінка на `fetch`, скрипт на `requests` або телеграм-бот;
- фільтри, пошук, пагінація по каталогу;
- throttling на створення заявок;
- `select_related` / `prefetch_related` і доказ, що запитів не побільшало;
- тести, що проходять;
- єдиний формат помилок для всього API.

## Ролі в команді

Ролей рівно чотири, і в команді вас четверо — **кожен бере одну**, без дублювання.
Роль визначає, хто пише і комітить, а не хто відповідає на демо: питання там
ставлять із **чужої** частини.

| Роль | Відповідає за | Файли |
|---|---|---|
| **Моделі** | моделі, міграції, `CheckConstraint`, адмінка, `seed_attack`, `contract.json`, README | `models.py`, `admin.py`, `seed_attack.py`, `contract.json`, `README.md` |
| **API** | серіалізатори, viewsets, router, `@action`-обгортки | `serializers.py`, `views.py`, `urls.py` |
| **Доступ** | права, власник заявки, коди відповідей, рядки 1–16 і 20 карти | `permissions.py` |
| **Стійкість** | `confirm` і `cancel` за схемою станів, гонки, веде атаку на 5-му уроці | `services.py` |

## Демо (урок 6)

**7 хвилин на команду, таймер видно всім.**

1. одним реченням — домен і обмежений ресурс;
2. `git checkout final` і `python tools/attack_open.py` наживо;
3. що пробили на атаці — і повторний запуск залатаних перевірок;
4. **по одному питанню кожному**: викладач показує місце в коді з чужої частини —
   пояснити, що там відбувається і чому саме так.

Пункт 4 — основний захист від «згенерували і не читали».

## Оцінювання

**Командна частина — 75 балів, однакова для всіх у команді.**

| Критерій | Балів | Коли рахується |
|---|---|---|
| Поріг: 7 рядків контрольної точки по 2 бали + робочий `seed_attack` і `contract.json` | 15 | кінець 2-го уроку |
| Відкрита карта, рядки 1–20, по 1 балу | 20 | тег `final`, на демо |
| Гонка А — одна заявка (рядок 21) | 5 | тег `attack` |
| Гонка Б — за ресурс (рядок 22) | 10 | тег `attack` |
| Закрита частина карти, захист | 15 | тег `attack` |
| Вільні атаки на ціль: одна вдала — 3, дві — 5 | 5 | 5-й урок |
| Командність: коміти від усіх, кожен у своїх файлах | 5 | історія git |

**Пробите на атаці можна частково повернути:** перевірка закритої частини або гонка,
залатана до тегу `final` і показана на демо, повертає половину своїх балів.

**Індивідуальна частина — 25 балів, у кожного своя.** Питання на демо: пояснив, що
відбувається і чому — 25; пояснив що, але не чому — 15; знайшов, де це в коді, — 5.

Додаткові пункти не дають балів — вони впливають на голосування команд за найкращий
проєкт (окрема номінація).
